# Game production and iteration workflow

Which player-facing uncertainty is worth resolving in this pass?

## When to repeat

At each milestone, after a playtest, or when scope and priorities change.
Run one focused pass for the current request; return when new evidence or changed
assumptions make another pass useful. Do not load every reference or rerun every
check on every minor edit.

## Bring forward

The creator brief, current playable build, remaining budget and findings from the previous pass.
If a previous record exists, review its decisions and unresolved findings before
planning. If it does not, establish a small baseline from the current game and
mark missing evidence explicitly.

## Run the cycle

1. Review the last pass before planning. Separate observed failures from preferences and untested assumptions. Preserve the current game identity, working mechanics and compatible progress.

2. Choose one learning question and an observable scenario. Prioritize blocked play or lost progress, then the brief’s experience goals. Decide whether this pass is a risk test, first playable, representative slice or milestone refinement; do not restart the project because a later stage looks attractive.

3. Make a bounded plan that fits the current tools and budget. Define a stop condition before adding art, systems or generated assets. Implement the smallest coherent slice that answers the question, following only the relevant technical guides.

4. Compile and play that scenario plus the affected recovery path. Compare the observation with the hypothesis. Keep, revise or abandon the decision based on evidence; use the installed independent review for an actual candidate.

## Verify and decide

A running build is not evidence of fun. Distinguish source checks, browser interaction, player observation and release receipts. Explain what the player could do, what changed, and what remains untested. Reading this workflow does not start another build or publish a candidate.

A traversal test reveals that players cannot see the landing. The next pass tests camera framing on that jump; it does not spend the budget on more rewards or a new level. Return to the same jump after a controller or camera change.

## Leave a record for the next pass

The scope decision, tested build revision, findings and one next learning question.

Record revision, question, bounded scope, scenario, observation, decision and next question. Carry only the evidence that affects the next pass; do not create a second backlog or mandatory production dashboard.

Use an existing project note or the handoff when no durable note tool is offered.
Keep facts separate from assumptions. The next pass should be able to recover
what was tried, why it was chosen and what the evidence established.
